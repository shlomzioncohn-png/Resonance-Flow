event pipeline

How a Kafka event actually gets from one service to another

One producer, one topic, one consumer, one registry checking both ends agree on the shape of the data. Every service in this system wires it up the same way — that's what makes one shared configuration pattern possible instead of a special case for each service.

02 · One shared file, one path variable

The connection itself is identical for every service — read its path, not six separate variables.

VariableLocal defaultMeaning
KAFKA_CONFIG_PATHclasspath:/kafka-config.yamlpath to the shared connection config file

Keys inside that shared file (read-only — you don't set these):

Your own settings — not in the shared file, set directly in your own service:

SettingMeaning
consumer group-idyour own consumer group id
consumer auto-offset-resetlatest, unless you have a reason for earliest
your topic namethe topic your event publishes/consumes on

03 · The one hard rule

→

One topic, one schema. Never route two different event shapes through the same topic, and never let two topics share a schema file — each schema declares its own kafkaTopic so the pairing is explicit, not implied.

There is no single shared schema — this diagram repeats once per event type. Today that's already four separate topic/schema pairs: task-event, task.created, bridge.raw.landed, bridge.github.tasks. A new event type adds one more pair to that list; it never joins an existing one.

04 · Wiring it up

Producer and consumer, reading the shared file plus your own settings — copied from a working setup already running in this repo (teams/relay), not hypothetical code.

kafka-config.yaml (shared, read-only)
spring:
  kafka:
    bootstrap-servers: kafka:29092
    properties:
      security.protocol: PLAINTEXT
      sasl.jaas.config:
      schema.registry.url: http://schema-registry:8080/apis/ccompat/v6
application.yml (yours)
spring:
  config:
    import: optional:${KAFKA_CONFIG_PATH:classpath:/kafka-config.yaml}
  kafka:
    consumer:
      group-id: your-service
      auto-offset-reset: latest
    producer:
      value-serializer: io.confluent.kafka.serializers.protobuf.KafkaProtobufSerializer
    consumer:
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.value.delegate.class: io.confluent.kafka.serializers.protobuf.KafkaProtobufDeserializer
        specific.protobuf.value.type: com.your.package.YourEvent

your:
  kafka:
    topic: your.topic.name
EventProducer.java
@Service
public class EventProducer {

    private final KafkaTemplate<String, YourEvent> kafkaTemplate;
    private final String topic;

    public EventProducer(
            KafkaTemplate<String, YourEvent> kafkaTemplate,
            @Value("${your.kafka.topic}") String topic) {
        this.kafkaTemplate = kafkaTemplate;
        this.topic = topic;
    }

    public void publish(YourEvent event) {
        kafkaTemplate.send(topic, event.getId(), event);
    }
}
EventConsumer.java
@Component
public class EventConsumer {

    private static final Logger log = LoggerFactory.getLogger(EventConsumer.class);

    @KafkaListener(topics = "${your.kafka.topic}", groupId = "${spring.kafka.consumer.group-id}")
    public void consume(YourEvent event) {
        log.info("Received event id={}", event.getId());
        // handle event
    }
}

YourEvent isn't hand-written — the Protobuf Maven plugin generates it from your .proto schema file at build time. No .toString() on the key: Protobuf has no native UUID type, so id fields are plain string and the generated getter already returns a String.

Full reference with rationale: teams/relay/src/main/proto/task-event.proto is a real, working example of a schema — kafkaTopic and all.
