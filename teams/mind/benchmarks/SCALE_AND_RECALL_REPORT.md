# Scale & Recall Validation — Response to PoC Review

This addresses the team-lead review of this PoC directly: the original
benchmark (`../../benchmark.py`) measured latency only, on 500 synthetic
random-word vectors — which proves the code runs, not that pgvector meets
Gong's actual requirements. This report adds everything the review asked
for: real data (with an explicit blocker flagged, not hidden), recall
measurement (not just latency), scale padding to the official 10,000-row
target, and an explicit meets/does-not-meet conclusion.

## TL;DR

| Question | Answer |
|---|---|
| Does pgvector meet the <300ms p95 latency target at 10,000 rows? | **Yes**, easily — p95 = 4.68ms, ~64x under budget. |
| Does the PoC, end-to-end, correctly find near-duplicate tasks at this scale? | **No — 0/8 (0%) recall** on the duplicate-pair test at pgvector's default settings. **This is the real finding of this report.** |
| Is that pgvector's fault? | **Mostly no.** Tuning HNSW's `ef_search` (never touched in this PoC — see below) fixes part of it and is free (no meaningful latency cost), but the dominant cause is the embedding model (`HashingVectorizer` — word-overlap only, no semantic understanding), not the index or the database. |
| Is real data being tested? | **No — BLOCKED.** No real data or loader exists anywhere in this repo (re-confirmed for this review, see below). A clearly-labeled placeholder is used instead; this is an open gap, not something to read past. |

## 1. Real data: BLOCKED, not substituted

The review asked for "a small slice of real data (a few rows from Yonit's/R2's
loader, or any real small sample we have)". Re-checked specifically for
this review, across **every branch**, not just `main`:

- No R2 loader exists anywhere (confirmed previously and again now).
- `origin/yonit/mind-data-models` exists, but contains only a Pydantic
  **contract** (`RawObjectEvent`) describing the *shape* of an event
  Bridge will publish when it lands raw content in MinIO (`object_key`,
  `source_type`, `tenant_id`, `content_hash`, ...) — no loader, no actual
  content, nothing fetchable.
- `eval/datasets/` is still empty except its README.

**Decision (confirmed with the team lead): proceed with a clearly-labeled
placeholder, flagged as BLOCKED, rather than wait or silently substitute
something else as "real".** [`real_data_slice.py`](real_data_slice.py)
generates 20 FUNSD-shaped placeholder records (form key/value text), every
one prefixed `realplaceholder-` in the table specifically so it can never
be mistaken for real data later. **This requirement is not satisfied by
this report** — it's exercised at the pipeline-shape level only. Re-run
`full_scale_benchmark.py` once real data lands (swap `real_data_slice.py`
for an actual fetch, same `(id, text)` return shape, nothing else changes).

## 4. Recall — the piece that was completely missing before

### 4a. Duplicate-pair recall (the business-relevant test)

8 pairs of near-duplicate task descriptions (same problem, different
wording — see [`duplicate_pairs.py`](duplicate_pairs.py)), e.g.:

> "Fix the login bug on the payments page" vs.
> "Payments page login button is broken, please repair it"

For each pair: embed one member, search, check whether the other member
appears in the top-k — **at pgvector's default HNSW settings**:

| k | Recall |
|---|---:|
| 5 | **0/8 (0%)** |
| 10 | **0/8 (0%)** |

**Zero.** Not one of the 8 paraphrased pairs found its partner, even
allowing 10 results back out of 10,000 rows. This is exactly the kind of
result the review warned about: latency looked great, and it was hiding
this.

### 4b. ANN-vs-exact recall (is the *index* the problem?)

To isolate whether this is the HNSW index approximating badly, or the
embeddings themselves being bad, the same query vectors were also searched
via **exact brute-force cosine** (all 10,000 vectors, computed in-memory)
and compared to what pgvector's HNSW index actually returned:

| k | ANN-vs-exact recall |
|---|---:|
| 5 | 60.0% |
| 10 | 61.25% |

So even independent of the duplicate-pair business test, pgvector's
**default** configuration only agrees with exact search ~60% of the time
at 10,000 rows — a real, measurable approximation cost that the original
latency-only benchmark had no way to see.

### 4c. Follow-up: is this fixable by tuning, or is it the embedding model?

`pgvector_store.py` never sets `hnsw.ef_search` (the standard runtime knob
that trades query latency for recall) — it's been running on pgvector's
default the whole time. Tested both the general ANN-vs-exact recall and
the actual duplicate-pair recall across `ef_search` values, on the same
loaded 10,000-row table ([`tune_hnsw_recall.py`](tune_hnsw_recall.py)):

| `ef_search` | ANN-vs-exact recall@10 | Duplicate-pair recall (5 / 10) | Query p95 |
|---:|---:|---:|---:|
| 40 (default) | 61.25% | 0/8 | 2.04ms |
| 100 | 62.50% | — | — |
| 200 | 63.75% | — | — |
| 400 | **86.25%** | **2/8** | 5.51ms |
| 1000 | — | 2/8 (plateau) | — |

**Two separate findings here:**
- General ANN recall improves substantially with tuning (61% -> 86% at
  `ef_search=400`) at **negligible latency cost** (p95 goes from 2ms to
  5.5ms — still ~54x under the 300ms budget). **This is a free, concrete
  fix pgvector_store.py should make regardless of anything else.**
- Duplicate-pair recall barely moves (0/8 -> 2/8) and **plateaus** even at
  `ef_search=1000` (25x the default). Raising the index's accuracy ceiling
  does not fix the real use case. **The dominant cause is the embedding
  model, not the index or pgvector itself** — `HashingVectorizer` matches
  literal word overlap, not meaning, so "login button is broken" and "fix
  the login bug" simply don't land near each other in hash space, no
  matter how exhaustively the index searches around them. This is the
  same root cause already quantified in this PoC's own earlier evaluation
  (`../semantic_quality/BENCHMARK_REPORT.md` §6): swapping to a real
  semantic model there raised precision from 41% to 68% on a similar test.

## 5. Explicit conclusion

**pgvector, as a database/index technology, meets the requirements
measured here**: latency is excellent and has headroom to spare at 10,000
rows (§3), and its recall ceiling with reasonable tuning (`ef_search=400`)
is 86% at effectively no latency cost (§4c). Nothing found here is a
reason to consider moving to Qdrant — the failure mode identified is
embedding-model-driven, not database-driven, and would reproduce
identically on any vector database fed the same hashing-vectorizer output.

**This PoC, as currently wired end-to-end, does NOT meet the real goal**:
0% recall on realistic near-duplicate detection at the target scale is a
hard failure of the actual product requirement, and it must not be read
past just because latency numbers look good. Root cause is the embedding
model, already flagged as a known placeholder in `../../mind_vector/embeddings.py`
and already being replaced in the production module
(`src/mind/embeddings/pipeline/` — currently MiniLM as a working fallback,
with BGE as the intended retrieval-tuned target, blocked on a local
network filter, not a code issue).

## 6. Warning signs / action items

1. ~~Set `hnsw.ef_search` explicitly in `pgvector_store.py`~~ — **done**,
   set to 400 (`config.HNSW_EF_SEARCH`) in both this PoC and the
   production store (`src/mind/embeddings/pipeline/pgvector_store.py`),
   based on the measurement in §4c.
2. **Real-data validation is still BLOCKED** (§1) — this must close before
   the PoC decision is considered fully validated, not treated as
   optional.
3. **Re-run this exact methodology** (`full_scale_benchmark.py`,
   `duplicate_pairs.py`, same 8 pairs) once a real semantic embedding
   model is live in production, to get the true end-to-end recall number
   — the 0% figure here is expected to improve substantially based on the
   production module's own before/after evidence, but that must be
   *measured*, not assumed.
4. Latency does not show growth with scale in the 500 -> 10,000 range
   tested — no action needed there, but re-check again once real load
   approaches production traffic patterns (concurrent queries, not
   sequential).
